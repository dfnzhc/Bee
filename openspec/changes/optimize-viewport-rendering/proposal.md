# Proposal

## Why

光栅化和路径追踪都在每帧重建内部执行图，并等待画面读回和打包后才开始处理下一帧。光栅化还会逐帧创建管线、目标图像和几何缓冲区，放大了相机操作到画面更新之间的延迟。

## What Changes

- 建立可重复的 Windows Release 性能基线，在相同场景和物理分辨率下对比停靠工作台、独立视口和仅渲染，记录各阶段耗时及输入到呈现的延迟。
- 缓存当前生效流程的执行计划和兼容的 GPU 资源。相机、模型变换等数据变化沿用原有计划，修改生效拓扑或资源契约时重新编译。
- 以有界异步交帧连接渲染器和工作台。空闲帧槽使用最新输入，减少读回路径上的整帧复制，并缩小画面更新的通知范围。
- 按网格、实例、材质和灯光增量更新 GPU 场景。模型变换复用静态网格及其 BLAS，曝光调整复用有效的 HDR 结果。
- 根据声明的依赖自动安排渲染工作，将足够大的独立 CPU 任务交给 Rayon。Vulkan 命令仍按计划在单队列提交。

前三项构成首批交付，在同一基线上验证后再推进场景增量更新和并行调度。D3D11/Vulkan 共享纹理及多 GPU 队列作为由性能数据驱动的后续验证。

### Modified Capabilities

- `render-graph`：复用生效执行计划，按已声明的 CPU 和 GPU 依赖安排工作。
- `interactive-viewport`：规定有界交帧、工作台更新的影响范围和可比较的性能验收。
- `path-tracing`：规定局部场景更新时的加速结构复用，以及累积历史的保留和重置。

## Impact

- `crates/renderer` 和 `crates/vulkan` 涉及执行计划、资源绑定、帧资源和 GPU 提交。
- `crates/scene` 涉及场景变更分类，`crates/bee` 涉及输入调度、视口呈现和性能诊断。
- `bee-renderer` 在并行调度阶段直接使用已在依赖锁文件中的 Rayon。
