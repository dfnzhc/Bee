# Design

## Context

停靠工作台通过 `Viewport` 共用相机输入、后台渲染和 GPUI 画布。当前鼠标处理更新 `SceneState` 后通知界面重绘，画布再延迟同步版本与尺寸。`Viewport::start` 已限制为一个在途任务，`generation` 目前同时随相机同步和视口状态变化推进。问题与行为要求见 [提案](proposal.md) 和 [视口规范增量](specs/interactive-viewport/spec.md)。

## Goals / Non-Goals

**Goals**

- 将启动相机渲染、交付已完成帧和判断是否需要下一帧放在共享调度路径中。
- 分开记录最新请求、已呈现的相机进度，以及决定帧能否用于当前视口的状态。

**Non-Goals**

本变更处理现有 Vulkan 读回到 GPUI 画布之间的调度与交帧。验收依据输入、渲染完成和画布更新的先后顺序。路径追踪采样语义以现有 `path-tracing` 规范为准。

## Decisions

### 相机变更直接进入单任务调度

拖动和滚轮在更新 `SceneState` 后通知 `Viewport`。视口可绘制且空闲时，立即使用当前快照启动任务。在途期间，`SceneState` 本身就是最新请求，完成后从当前状态再取快照。光栅化呈现最终视角后进入空闲。这使待处理工作量不随输入次数增长。

画布仍负责报告物理尺寸和绘制最新接收的图像。首次取得有效尺寸或恢复可绘制时，由尺寸同步提交当前请求。已有场景、参数和流程变更入口接到同一调度路径。

### 将相机进度与帧兼容性分开

用 `generation` 标记视口尺寸、可见周期和已生效流程的变化。隐藏后以相同尺寸恢复，或在同一模式下成功应用不同流程，都要使旧任务的标识失效。完成时还要校验当前的场景、渲染参数、显示参数和模式，以覆盖已更新但尚未同步到视口的状态。

相机使用 `Versions.camera`，与已有的 `image_versions` 比较。只要成功结果仍与当前视口兼容，且相机版本不早于已显示画面，就可以接收。首个兼容成功帧可直接建立画面，同一相机可以呈现更新流程后的首帧和后续光追样本。只更新目标相机时，继续绘制已有图像，直到新帧可用。接收时一并更新图像、版本和对应样本数，再通知 GPUI 重绘。

### 优先处理新的目标相机

每次完成后，无论结果被接收还是失效，都检查是否有更新的可绘制请求，并在有待处理请求时立即启动。这样最终相机可以在没有后续鼠标事件时抵达画布。当前请求成功呈现且没有更新目标时，路径追踪才按现有定时方式继续采样。续采回调需要核对原请求的版本与视口标识，避免旧定时任务在相机变化后重复派发。

`PathRenderer` 按实际渲染的快照管理累积历史。新的相机快照从首个样本开始，稳定的相机继续累积。

## Risks / Trade-offs

- **视口兼容性变化。** 延迟的画布尺寸同步和在途回调都需检查当前视口状态。在首帧、隐藏恢复、调整尺寸和应用流程的场景中验证下一份有效请求能够启动。
- **渲染失败与关闭。** 放宽交帧条件仅适用于成功结果。最新请求失败时走现有诊断，已被取代的请求失败时保留当前图像并处理更新请求。关闭沿用在途 Vulkan 任务先完成并释放资源的约束。
- **界面重绘可能合并。** 回归检查需要验证帧完成时发出重绘通知，并观察拖动期间画布绘制了不同的相机帧。
