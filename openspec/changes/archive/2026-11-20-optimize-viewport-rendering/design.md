# Design

## Context

`Viewport::start` 通过 GPUI 后台任务运行整帧，并在完成回调里选取下一份快照。`GraphResources::submit` 每次编译 `WorkGraph`，而 `WorkPlan` 既包含拓扑顺序，也包含从当前资源用途推导出的 barrier。`WorkPlan::record` 在单个 `Frame` 上录制。当前实现已能合并相机输入和保留最后可显示画面，这些交互语义是异步交帧的基础。

## Goals / Non-Goals

**Goals**

- 让编辑流程的生效周期、帧状态和 GPU 资源生命周期各自可验证。
- 让渲染器和呈现端在有限的在途容量内独立推进，再以性能基线决定 CPU 工作的并行粒度。

**Non-Goals**

- 首批交帧采用 GPUI 的读回路径。D3D11/Vulkan 共享纹理和多 GPU 队列在对应开销有实测依据后各自验证。

## Decisions

### 用同一套观测点比较三种运行方式

记录构建版本、设备、场景、物理宽高、预热与采样窗口、渲染模式和光追参数。停靠工作台、独立视口和仅渲染使用相同的渲染器和帧输入序列。仅渲染模式完成同等场景与色调映射工作，在输出图像就绪后结束；可见配置继续计时读回、CPU 像素处理和 GPUI 上传。CPU 侧记录阶段时间和资源操作计数，GPU 侧在目标队列支持时用 timestamp queries 计时。

用相机版本和帧标识关联输入、有效提交、读回就绪、CPU 交付及桌面呈现事件。可见配置的输入到呈现 `p95` 取对应实际呈现的帧，同时报告被合并的输入比例和最终视角延迟。原生呈现时间与测试画布或 UI 绘制时间分别记录。首批完成后复用同一套输入、尺寸和参数对照，其中包含一组全屏物理分辨率样本。

### 将可复用计划和运行时状态解耦

应用草稿时验证模块连接，从视口输出提取可达工作，为生效拓扑及资源访问契约编译不可变的 `WorkPlan`。计划保留逻辑资源、依赖和所需阶段及访问类型。每帧按逻辑 ID 绑定实际资源，用当前用途、布局和所有权补齐导入及跨帧 barrier；按已提交的顺序跟踪用途，按完成信号回收资源。绑定修订号只用于保护绑定和资源状态的一致性。

计划编译和 Vulkan 管线创建分别缓存。相机、实例、材质、灯光和曝光属于运行时数据；兼容的尺寸变化重新建立对应目标、读回资源和光追历史。首批先缓存按场景版本生成的光栅几何缓冲区，确保相机运动走纯帧数据更新，场景增量阶段再细化缓存粒度。曝光更新在拥有当前 HDR 结果时复用显示子计划，有效结果缺失时使用完整计划。

新的候选流程通过验证和计划准备后一次替换生效状态。渲染中的快照继续持有原计划和资源，编译失败时原流程仍可呈现。仍在执行的资源只因最后使用者完成而回收。

### 用有界帧槽异步交帧

渲染协调器持有执行计划、帧槽和最新输入。起步使用两个可复用帧槽，各自持有命令池、帧数据、目标及读回资源。协调器有空闲帧槽且依赖就绪时取最新输入。未提交的过期请求可合并，槽满时保留一个最新待渲染状态。渲染侧通过 GPU 完成信号推动后处理和资源回收，UI 侧使用完成的图像。静止续采由协调器按可见状态和容量驱动，相机更新优先于续采。

GPU 完成后才读取像素。色调映射优先直接写支持所需用途的可读回 BGRA 目标，兼容回退在一次 CPU 像素处理中完成转换。已紧密排列且拥有独立存储的像素直接移交 `RenderImage`。帧槽只等待仍实际引用其资源的参与方。按视口兼容代际和呈现版本接收结果，迟到帧按已有交互规则推进或丢弃。缩放、关闭和换流程同样经过有界退役，通知只发给视口及需要显示渲染状态的组件。

### 按依赖更新 GPU 场景与光追历史

以对象空间网格作为几何缓存，按网格、实例变换、材质及光源分别判断更新。光栅读取实例缓冲区中的变换，光追用每网格 BLAS 和实例化的 TLAS。构建条件兼容时更新 TLAS，条件变化时重建 TLAS，仅重建变更网格对应的 BLAS。变换后的顶点、法线和材质索引要与两条路径的场景定义一致。

用历史键标记相机、场景、追踪设置和输出尺寸。历史写入按提交顺序串行，首样本覆盖，后续样本读取并更新同一历史。用预编译的首样本和续采访问变体表达两种访问，轮换代际时同步旧使用者。曝光使用同一份有效累积图，呈现的样本数跟随实际交付的结果。两个帧槽可以重叠 CPU 和 GPU 阶段，但同一历史的相依读写始终遵守 GPU 顺序。

### 用现有图表达依赖，用 Rayon 执行就绪的 CPU 工作

在编译计划时生成 CPU 任务的前置计数和后继关系。准备或录制任务在自身前置完成后进入就绪队列。GPU 资源依赖单独约束提交顺序与可见性。上传及加速结构准备和构建纳入依赖声明，barrier 使用真实的生产与消费阶段。比如绑定完成后可分别录制场景和色调映射，但 GPU 仍需在场景颜色可读后执行色调映射。

使用渲染器常驻的 Rayon 线程池运行有足够工作量的任务。并行录制采用按帧槽、按工作线程归属的命令池，提交线程汇总缓冲区并在单个 Vulkan 队列提交。小批次沿用顺序执行。通过受控分支用例验证依赖就绪规约，再在多绘制批次的场景中以录制耗时与 `p95` 选择并行粒度。

## Risks / Trade-offs

- 帧槽过多会增加显存和输入排队延迟 → 从双槽起步，合并最新输入并对照测量后确定容量。
- 资源状态因重绑、外部消费或异常变得过期 → 使用实际用途和完成事件维护状态，用验证层覆盖资源替换、迟到完成和关闭。
- 录制并行的分发成本超过收益 → 保留串行执行并对同一工作量测量不同粒度。
- 只测 GPU 结果或模拟画布会掩盖工作台交帧成本 → 以可见配置的原生呈现数据验收，独立报告仅渲染和模拟场景的结果。

## Migration Plan

先保存改动前基线，再落地计划与资源复用和异步交帧。首批验收通过后执行场景增量更新和并行调度。每组同步更新回归用例。若新流程准备失败，保留现有有效流程；若阶段改动导致回归，依照基线撤回该阶段实现后重测。
