# Design

## Context

当前 `crates/bee/src/main.rs` 由一个 `Bee` 根视图持有 `SceneState`、`Viewport` 和设备信息；视口自身持有 `FlowEditor`。`SceneState` 提供场景、相机和版本化快照，场景使用实例、材质和光源数组，没有名称或层级。`Viewport` 通过后台任务将 Vulkan 结果读回，再以 GPUI 图像显示，并通过尺寸、版本和 generation 区分请求。

应用固定使用 GPUI 0.2.2；现有 Windows 接入结论针对该版本。设备报告与视口错误写入标准错误，Vulkan 验证消息从底层回调直接写入标准错误。规格见 `editor-workbench`、`workspace-files` 和 `editor-console`；原有视口、流程和渲染规格继续适用。

## Goals / Non-Goals

**Goals:**

- 在保持真实渲染状态和诊断可见的同时，将面板布局与场景、视口及流程状态分离。
- 优先复用可验证兼容的 GPUI Kit 组件，保持各面板独立呈现但共享同一份应用状态。
- 覆盖停靠操作引入的视口显示、隐藏、尺寸和后台任务生命周期变化。

**Non-Goals:**

- 不引入场景文档、稳定对象 ID、场景层级、撤销栈或资源管理系统；不重做节点画布。
- 不要求跨原生窗口停靠、多视口、布局跨进程保存或新增零拷贝图像共享路径。
- 不将文件浏览扩展为资源导入、文件编辑或场景保存。

## Decisions

### 1. 单窗口工作台与统一视觉语言

采用单原生窗口内的可停靠工作台。默认左侧为场景树，中间为主视口，右侧为属性；文件、控制台和 Render Flow 默认作为底部标签页。菜单或等效入口负责显示被关闭的面板和恢复默认布局；分区可缩放，标签可拖动到其他停靠位置。关闭、移动或重置布局只改变界面结构，不销毁场景、相机或流程草稿。

风格参考 GPUI Kit 演示：深灰分层背景、细分隔线、紧凑工具栏、清晰的选中与焦点状态。统一定义背景、面板、边框、正文、次要文字和强调色；可以暗金作为强调色，状态配合文字或图标，不单靠颜色。默认左右面板约 240/280 逻辑像素、底部约 200 逻辑像素，再按窗口可用空间收缩；小窗口允许面板滚动和切换，不能通过固定宽度挤掉主要控件。以 960 x 640 逻辑像素和 Windows 系统缩放作为基本检查场景。

替代方案是保留固定双栏或为每个面板开启独立原生窗口。前者无法满足面板停靠要求，后者增加窗口和图形资源管理复杂度，均不作为首版。

### 2. 先验证 GPUI Kit 兼容性，再选择接入方式

先选取可用的 GPUI Kit 版本，验证 Dock、基础控件、原生文件夹选择和现有 GPUI 图像绘制能否在同一应用中编译运行。GPUI 类型必须来自兼容的同一依赖来源；不能把不同 crate 或版本的 `App`、`Window`、视图和上下文类型当成可直接互换。若需要升级 GPUI，同时调整应用、测试依赖及构建锁定，并重新验证 Windows 视口和现有测试。

优先复用兼容版本的 GPUI Kit 停靠及基础组件。若无法找到满足要求的组合，使用当前 GPUI 构建仅覆盖本次面板需求的停靠交互，仍须满足拖动、调整、关闭、恢复及视口验收；不得以静态分栏替代这些要求。无论方案如何，不预设新的 GPUI 版本支持跨 API 共享纹理；未完成实际验证时沿用可诊断的异步读回接入，并更新版本相关说明。

### 3. 应用状态保持单一来源

工作台拥有面板可见性、布局和只读选择状态。场景树直接从 `SceneState` 的实例、光源及独立相机生成分类与临时显示标签，选择以当前场景中的类型与索引表示；场景替换或索引失效时清除选择。属性面板读取同一份场景数据，必要时以现有变换表示展示，不为了显示而改写场景。

保留单一 `Viewport` 和单一 `FlowEditor` 实例及其生效/草稿状态；面板只提供访问这些状态的视图。视口快捷按钮与 Render Flow 继续作用于同一流程。选择、切换标签或仅改变焦点不能递增场景及相机版本，也不能在尺寸未变时重置路径追踪采样。这样可以避免为尚未实现的编辑功能引入第二份文档模型或 ECS。

### 4. 视口随面板可见性和尺寸正确恢复

保留异步读回、快照与 generation 的所有权边界。面板拖动和分区调整以实际可绘制区域及设备缩放更新视口尺寸；不可绘制或隐藏时停止继续提交无效尺寸的工作，重新显示后以当前场景、相机和流程恢复。后台结果必须经过当前尺寸、可见性及 generation 检查，过期结果不能覆盖新状态；在途 GPU 资源仍按提交完成情况释放。

面板重排不应重复创建互相竞争的渲染器，也不能将 GPUI 的绘制对象传播到场景或渲染算法层。保留设备能力、路径不可用原因、样本数、读回方式及失败提示；曝光与场景变化对累积的既有语义不变。

### 5. 文件浏览和诊断分别接入真实来源

文件面板通过文件夹选择器获得用户选择的路径，只读取当前目录条目，使用文件夹/文件的不同标识并提供返回上级。目录读取放在不会长期阻塞界面的路径中；路径变化后忽略旧读取结果。取消选择不清空原位置，空目录、权限错误和目录消失均有明确反馈。无需扫描整个目录树，也不提供导入或写操作。

在创建设备之前建立有界诊断接收端，确保启动及初始化失败信息可以进入控制台。应用设备报告、视口和流程错误接入同一显示列表；Vulkan 验证回调将消息安全地传递给接收端，同时保留现有标准错误输出。回调可能在非 UI 线程执行，因此不得直接操作 GPUI，使用有界、非阻塞传递并在界面线程更新；消息丢弃需可见。回调上下文必须在相关 messenger 及在途回调结束前保持有效，FFI 回调不能向外展开 panic。筛选仅改变可见内容，不删除历史。

替代方案是只解析或截取标准错误；它难以可靠区分来源和级别，也无法直接控制回调资源生命周期，因此优先在消息产生处接入。无需为此建立通用插件或远程日志系统。

## Risks / Trade-offs

- [GPUI Kit 与当前 GPUI 不兼容] → 先完成版本和 Windows 画面接入验证；采用可工作的兼容组合，必要时使用 GPUI 原生停靠实现，验收范围不缩水。
- [拖动或隐藏视口使旧帧、资源或后台任务越过生命周期] → 在停靠、隐藏、恢复、连续调整和最小化场景覆盖实际窗口与 Vulkan 验证层检查。
- [诊断回调与 UI 生命周期交错或消息过多] → 在设备初始化前创建接收端，使用有界非阻塞传递，明确关闭顺序，保留终端输出并提示丢弃。
- [场景数组索引被替换后指向其他项目] → 选择仅供只读界面使用，场景替换或索引失效时清除，不将临时标签当作稳定对象 ID。
- [异步读回或大目录影响交互] → 合并过期请求并避免 UI 线程长期阻塞；本次不设置未经测量的帧率门槛。

## Migration Plan

先验证组件依赖与现有视口，再接入工作台和各面板，最后回归现有渲染与设备测试。若升级 GPUI，构建依赖和文档作为同一变更处理；回退该变更应同时恢复原依赖和原窗口。没有用户场景或项目文件需要迁移，布局跨会话持久化不属于本次验收。
