# Design

## Context

项目当前只有基础说明和 OpenSpec 配置，没有渲染器代码或既有规格。目标及第一版边界见 `proposal.md`，可验证行为见 `specs/`。

Windows 是首个开发平台。三维画面必须由自研 Vulkan 封装和渲染器产生；GPUI 使用其自身的界面绘制方式。两者的纹理共享、格式、设备匹配和同步尚未经过项目内验证，不能仅凭扩展名称推定可用。

## Goals / Non-Goals

**Goals:**

- 定义应用状态、算法模块、渲染图、自研 Vulkan 后端和画面接入层之间的职责。
- 让第一版的两条独立渲染路径使用相同场景，并通过算法模块图接入视口。
- 先建立可验证的正确性、资源生命周期和诊断，再依据实际问题优化。

**Non-Goals:**

- 不提前实现 D3D、Metal 后端或为假想后端建立完整图形抽象层。
- 不要求 GPUI 使用自研 Vulkan 后端，也不在第一版实现光栅化与路径追踪融合。
- 不实现离线导出、实时降噪、复杂材质和资产导入、节点插件系统或多队列调度优化。
- 不设置帧率、延迟或其他性能数值验收门槛。

## Decisions

### 1. 界面、应用状态与场景渲染独立

GPUI 负责窗口、布局、输入、节点界面和视口呈现；应用层维护场景、相机、节点图及其变更版本；渲染器读取一致的场景状态并负责全部三维画面。画面接入层负责将渲染结果交给界面，不能把 GPUI 内部图形对象传播到场景或算法模块。

首个场景使用内置几何体、基础漫反射材质、光源与相机。两条路径读取相同的数据和坐标约定。相机输入和场景变更由应用层传给渲染器；线程、帧提交和资源释放的所有权必须明确，不能让界面修改正在被提交使用的数据。

选择此边界是为了让编辑器和三维渲染独立演进。替代方案是让 GPUI 直接拥有场景绘制或强行统一两个绘制后端，但它们都不符合当前边界，也会增加首版集成工作。

### 2. Vulkan 优先，按实际需要封装

使用 Vulkan 的 Rust 原生绑定作为 API 入口，在项目内负责设备、队列、资源、命令提交、同步、管线和错误处理。绑定只提供 API 调用能力，不替代自研渲染器；可优先评估 `ash`。设备初始化分别检查基础图形能力和路径追踪能力，包括必要的扩展、feature 和属性。缺少后者时保留光栅化；没有基础图形能力时明确报告失败。

着色器采用可复现的 SPIR-V 构建流程，并明确记录构建工具与错误。开发配置支持 Vulkan 验证层。资源延迟释放以实际提交完成为准，不能假定 CPU 帧结束代表 GPU 已完成。

与现在就设计统一的跨 API RHI 相比，这个方案保留 Vulkan 的能力和诊断，同时避免在只有一个后端时预设不准确的共性。

### 3. 可视化算法图与内部执行图分层

用户编辑的节点图只包含有实际用途的算法模块：光栅化、路径追踪、色调映射和输出。默认流程分别为：

```text
光栅化 ──┐
         ├──> 色调映射 ──> 视口输出
路径追踪 ─┘
```

示意图表示两条可选连接；第一版某次生效的流程选择其中一条，不要求融合。节点有明确的输入、输出和参数；编辑结果先验证类型、必需连接和循环，再作为一个整体生效。无效编辑保留上一份可执行流程并显示尚未生效的状态。第一版不要求持久化节点图或提供通用插件注册机制。

每个算法模块向内部执行图声明实际 GPU 工作，以及资源的读取、写入和用途。执行图按依赖排序，生成必要的 Vulkan 同步和布局转换。读取未定义内容、无明确先后关系的冲突写入或无法满足的输入必须在执行前报错。模块可以展开为多个工作步骤，而不将这些步骤暴露为用户节点。

资源按临时、跨帧历史和外部资源区分生命周期；场景颜色使用明确的线性颜色约定，色调映射和输出边界负责显示转换。外部资源的使用权与交接同步由接入层共同约定。未来的混合流程可以新增模块和输入，并复用资源声明和依赖管理；本次不实现混合算法、内存别名或异步计算。

替代方案是让节点直接对应每一个 Vulkan pass。该方式会将实现细节暴露给用户，也会把用户的流程绑定到具体算法实现。

### 4. 两条路径共享场景，各自完成完整渲染

光栅化路径构建正常的图形管线，绘制内置场景并进行深度测试和基础直接光照，输出场景颜色。

路径追踪路径使用设备的 Vulkan 光追流水线、加速结构、着色器绑定表和相应着色器。先支持漫反射、至少两次表面交互、简单场景光源及可见性；基于随机采样累积直接与间接照明。直接光采样和后续路径贡献需使用一致的概率和权重，避免重复计入同一光路。第一版可以使用简单点光源和环境光，将更复杂的材质、光源采样和降噪留待后续。

路径追踪以累积颜色和样本计数维护历史。相机、几何体、材质、光源、影响追踪的参数或输出尺寸变化时，新的历史从零开始；仅影响显示的色调映射参数不应迫使有效的路径采样历史重置。运动中允许噪点，静止后持续增加样本。帧间资源和重置必须与实际 GPU 提交同步，避免旧帧写回污染新历史。

替代方案是先实现只有主光线和直接照明的演示，但它不能满足第一版路径追踪的目标。第一版也不以静止收敛速度或运动中的噪点为性能门槛。

### 5. 先验证 Windows 画面接入，保留明确的回退

在开发两条完整算法之前，先用自研 Vulkan 绘制可识别测试画面，再将其显示在 GPUI 视口中，覆盖初始化、调整尺寸、最小化和恢复。该闭环只验证基础接入，不代表光栅化和路径追踪已经完成。

优先验证 GPU 共享纹理：确认 GPUI 的可接入位置、双方设备是否匹配、所选纹理格式与句柄类型能否导入导出，以及双方可用的同步机制和所有权交接。必要时只在界面接入边界适配 GPUI；不修改三维渲染责任的归属。不预设某个扩展、同步句柄或 GPUI 接口一定可用。

若共享纹理不可用，使用 Vulkan 输出的异步读回和 GPUI 可接受的图像上传作为第一版回退，标识当前接入方式，并正确处理行跨度、颜色、尺寸和资源生命周期。若回退也失败，显示明确错误。回退可能增加拷贝和延迟，但不会引入帧率验收门槛。直接假定零拷贝已经可用会使框架建立在未经验证的接口上。

### 6. 验证行为而不是预设速度

用针对性的自动测试验证图合法性、资源依赖、场景变更和累积重置；在支持相应硬件的 Windows 环境中运行两条路径的端到端检查与 Vulkan 验证。使用固定场景、可控随机种子或可检查的简单照明关系验证正确性，不将某一张含噪图像的逐像素相等作为路径追踪标准。

开发者记录设备、驱动、可用功能和接入路径，方便复现问题。完成框架后可建立性能基线，但本变更不预先规定帧率或优化数值。

## Risks / Trade-offs

- [GPUI 的外部纹理接入或跨 API 同步不可用] → 先做独立接入验证；保留可识别的读回上传回退，不把共享纹理写成必然成立的前提。
- [双显卡机器上的界面设备与 Vulkan 设备不一致] → 在共享前核对设备标识与句柄兼容性，无法匹配时选择回退并报告。
- [路径追踪能力不足或驱动存在差异] → 按 feature、扩展和属性检测，并让光栅化保持独立可用。
- [跨帧累积和异步资源交换出现竞争] → 以提交完成信息和明确的资源所有权管理重置、替换与释放，并覆盖尺寸变化和连续相机操作。
- [首版范围较大] → 先验证框架和画面接入，再逐步完成两条路径和节点界面；只有两条路径都符合规格才算第一版完成。

## Migration Plan

这是空项目中的新增能力，无既有数据迁移。按任务清单分阶段建立可运行闭环；任一阶段未完成时不得将该阶段的结果当作完整第一版。若实现方向需要调整，可撤回尚未发布的新增组件和依赖。
